# 设计说明

## 架构（full-context 优先）

```
report.md（auto-023 产物，约 8K 字符 ≈ 10K token；锚点即引用体系）
   ↓ 全文作为上下文（[R] 拒答清单与 [T] 模板随全文天然在场）
LLM（OpenAI 兼容，可插拔；未配置→诊断模式；故障→错误码，不编造）
   ↓ 确定性保证（与模型无关）：
     · 引用锚点校验（未知锚点告警）
     · 数据版本声明 footer 由流水线追加
result JSON（answer/citations/version）
```

## 为什么不做检索（Owner 2026-10-22 确认）

- 报告仅 ~8K 字符，远低于现代上下文窗口；全上下文召回率 100%，零检索代码，锚点引用天然准确；
- Python 标准库无 RAG/检索组件；成熟方案（LangChain/LlamaIndex、向量库、embedding 模型）在 8K 文档上是纯负担；
- 早期版本曾自建 TF-IDF 检索器，已删除——这正是"不为小文档造 RAG"结论的来源。

## 升级路径（何时重新引入检索）

触发条件：知识库超出上下文预算（`pipeline.CONTEXT_CHAR_BUDGET = 60_000` 字符，约 40K token）——例如案例扩容、多份报告合并、明细数据接入。届时：

1. 首选**成熟方案**：LLM 服务商 embeddings API（OpenAI 兼容 /embeddings）+ 标准向量检索，或 LangChain/LlamaIndex 的检索组件——不自建打分逻辑；
2. `pipeline.ask` 增加检索分支，其余保证（版本声明、锚点校验、拒答注入）不变；
3. 报告自身按锚点切块即可（[K]/[D]/[F*]/[C]/[R]/[T]），无需重写内容结构。

## 确定性保证（与模型无关）

- 数据版本声明：流水线追加到每个回答末尾；
- 锚点校验：回答引用的 [XX] 必须存在于报告，未知锚点告警；
- 拒答与模板：随全文在场；
- LLM 故障：返回错误码 + 诊断信息，不输出编造内容；
- 问答日志：output/qa-log.jsonl（未来缺口日志的数据源）。
