# Design

## Context

参见 `proposal.md` 的产品目标与 MVP 范围；可观察行为以 `specs/report-orchestration/spec.md` 为准。

- `06_reporting/agent-kb/` 已能从冻结分析数据构建静态报告 HTML、机器可读 Markdown、`numbers.json` 和版本元数据；当前章节/发现文案来自人工维护的 `configs/content.json`，构建器主要做数字填充与渲染，不负责发现分析。
- 当前报告 README 将其标为上一版数据上的临时、未验收产物；报告声明样本截至 2026-10-03。已发现封面称舒适性负面声量占比最高，但同份报告表格给出可靠性 55.1%、服务 47.0%、舒适性 43.4%，因此不得直接发布或作为最终问答知识库。
- `07_qa_agent/` 目前提供 CLI，全报告上下文问答，校验报告锚点并追加版本信息；模块没有 Web 服务接口。
- 现有变更材料提到观点证据，但观点记录的稳定主键及供查询服务使用的标准化输入，需要实施前从实际数据文件核对。
- `data-audit.md` 已记录实际审计：范围为 9,529 帖/26,936 声明/15,002 提及（2022-10-28 至 2026-10-03）；精选 core/potential 合计 819 条、均有 URL 与 evidence，但不是全量声明。当前快照版本标签明确为占位性质。CSV `negativeShare` 实际是负面声明/声明总数（131/302），负向帖子计数 113/239 是另一单位；候选议题精选证据 44 core + 38 potential，产品必须显示不同分母并声明精选覆盖限制。
- 比赛要求公网智能体链接；具体云平台、比赛评分细则和可公开数据授权当前未知。Owner 批准规格后、开始发布内容前须确认数据展示边界。

## Goals / Non-Goals

**Goals:**

- 用最小可部署 Web 产品实现报告、问答和对话式下钻的连续体验。
- 从研究任务定义和冻结数据生成报告草稿，经机器可验证门禁与团队审阅后发布。
- 让 Agent 通过受控只读工具查询统计和用户观点，明确展示统计口径、样本量、数据版本和证据。
- 让静态报告在 LLM 或 API 故障时继续可读；部署密钥只存在服务端环境。
- 把统计工具、Agent 编排和 Web API 解耦，以便后续需要多消费者时接入 MCP。

**Non-Goals:**

- 不搭建可配置任意指标的通用语义平台；MVP 只覆盖演示所需且现有数据能支持的指标和切片。
- 不实现多 Agent、全量报告自动重生成、无人审批自动发布、自动数据采集或跨期差异分析。
- 不将 LLM 文本自评、词表命中或模型裁判作为结论正确性的证据。

## Decisions

### 0. 模块边界与目录职责

在线服务按 API 入口、意图路由、研究/统计语义、Agent 工具与编排、报告审核发布划分职责。HTTP handler 只校验请求并选择用例，不直接实现分类规则、指标 SQL 或报告门禁；所有消费者（Web API、深度 Agent、MCP）复用同一研究语义层。当前从根目录平铺模块逐步整理为显式 Python 包，迁移期间保留兼容导入，避免破坏已有脚本和测试。

### 0.1 上下文对话 Agent

主提问入口把用户消息和最近会话交给一个对话 Agent。Agent 直接回答普通交流，必要时选择报告检索、统计、观点证据或代码分析工具；独立分类模块不再参与主链路。追问结果来源时提供上一轮实际结果作为上下文。代码工具继续限制在语义层沙箱；完整报告使用显式报告入口及其计划与发布校验。

### 0.2 业务分析维度目录

研究 brief 以显式指标定义（标识、业务含义、单位/分母、数据来源、适用范围）和分析维度定义（标识、字段来源、总体或精选证据范围、支持的查询方法、缺失值语义）约束“数据→发现→报告”。帖子级和观点声明级指标分开；`journey`、`ownership`、`experience`、产品共现及时间切片标注为精选证据子集，不推断为全量总体代表。报告章节需求映射到 brief 的研究问题与方法，不允许报告写作技能自行补充未查询的维度。

### 0.3 只读 MCP 适配器

实现可由标准 MCP 客户端启动的只读服务器，复用语义服务和预置方法目录，只暴露健康状态、指标/方法目录、统计查询、精选观点查询和白名单分析方法；不暴露 SQL、文件系统、Agent 任意 Python、审核/发布写接口或密钥。使用官方 Python MCP SDK 的 stdio transport；HTTP Web 服务继续直接调用相同应用层函数。SDK 缺失时启动应明确报依赖错误，不静默降级为其他协议。协议入口与语义查询分离，MCP 测试可在不安装 SDK 时验证共享语义层和输入/输出边界；完整握手验证需在装有 requirements.txt 的目标环境运行 MCP Inspector 或官方客户端。

### 1. 单体部署，模块内分层

比赛 MVP 使用一个 Python Web 服务进程，同时托管静态前端资源与 API；统计查询、观点查询、Agent 编排各自独立为 Python 模块。静态报告构建产物和选定数据快照随发布包只读挂载。部署平台选择由 Owner 根据学校/比赛环境确定，接口与镜像不绑定某个云厂商。

**理由：**三人团队可少维护一套运行环境和跨进程协议，同时保留清晰模块边界。替代方案是将前端、API、MCP 服务分别部署；它改善独立扩缩容和复用，但对当前单个演示产品增加运维与集成成本。

### 2. Web 与 MCP 共用类型化研究语义接口

统计、精选证据、指标/维度目录及预置方法属于研究语义层；Web handler、Agent 工具和 MCP server 是独立适配层。MCP 仅通过 stdio 公开有限只读工具，应用层接口不依赖传输协议，且输出使用统一的数据版本、样本和口径信封。若目标环境无法安装 `mcp` SDK，则保留依赖及明确启动错误，并将 MCP 客户端握手列为未验证项；不得把 Python 函数调用或 skills 描述为 MCP 实现。

**理由：**用户要求当前交付含有真正的标准协议入口，不能把“未来可接入”当作已实现。适配层与业务层解耦，避免把 MCP 工具注册、传输处理和统计口径混在一起。

### 3. 按职责分包并保留兼容入口

把入口适配、路由、研究目录/查询和 MCP 适配分别放入职责明确的包；历史顶层导入保留兼容转发，避免破坏现有脚本、Agent 与测试。每一项业务定义只保留一个权威目录，brief 仅选择目录中的 ID，不复制口径值。

**理由：**当前职责已拆成多个文件但仍平铺于一个目录，业务口径亦在 brief、目录和方法说明重复出现。保持旧模块路径可减少迁移风险。

### 3. 统计值由快照/代码计算，语言模型负责问题规划与解释

查询层读取版本固定的分析快照及经核对的观点数据索引。首版指标目录仅声明演示涉及的口径、分母、适用群体、最小样本量和切片条件。CSV 的 `negativeShare` 是观点声明级比例，计算为负面声明/声明总数；`negative_posts/posts` 是独立的帖子级计数。工具不得将两种分母混称。工具返回标准信封：`data`、`caliber`、`data_version`、`n`、`warnings`、`truncated`。Agent 通过工具选择分析条件，再组织自然语言解释。

模型输出不承担统计计算。返回 UI 时，数字、口径、版本、样本量和来源清单以结构化字段独立呈现；说明文字不得替换工具返回的结构化统计值。对无法由工具结果和证据支持的断言，拒绝生成或明确标为证据不足。

**理由：**结构化字段便于精确校验和展示，叙述质量再由队友审核。替代方案是让模型自由生成长篇文本，再用关键词或模型自评判真伪；这种检查无法可靠证明结论正确。

### 4. 观点引用使用快照内可复现的版本化标识

在构建观点索引时，为每条记录生成限定于 `data_version` 的 `claim_id`，并保留来源帖子标识、记录序号、引文、链接、议题、情感和表达边界。标识生成规则须确定性且在同一快照重建后不变；不承诺跨数据版本保持同一 ID。上线前核对来源字段与链接可展示性。

**理由：**能支撑单期演示引用，同时避免在源数据尚无全局主键时声称跨期身份稳定。替代方案是先改写 04/05 上游数据契约；这会扩大 Change 和集成面，后续确有跨期追踪需求时再处理。

### 5. 报告由研究任务定义驱动生成并经团队审核

团队维护 `research-brief.json`：研究问题、适用群体、指标 ID、比较维度、最低样本阈值、要求的证据类型和覆盖范围。它定义研究设计，不包含当期结论或手写发现段落。单 Agent 使用 `query_stats` 与 `query_claims` 分析冻结快照，生成结构化 `content.json` 草稿；每个发现拆分为：观测事实（指标值与比较条件）、支持证据、解释/假设、限制/替代解释、建议/待验证问题。事实字段由工具结果引用，LLM 不计算数字。

离线生成流程执行确定性质量门禁：报告 schema、研究问题覆盖、数字与口径来源、证据 ID 有效、引文与冻结来源一致、版本一致、样本阈值和必要限制说明。门禁通过只表示结构及可核验字段通过，不表示分析质量已获证明。报告随后进入待审目录，由一名作者和至少一名队友复核重点发现、证据代表性、解释越界和业务表达；明确批准后才生成部署用静态报告与发布记录。门禁失败或人工未批准时，草稿不进入公开报告目录；已有已批准版本保持在线。

深度 Agent 提交的 Markdown 使用同一发布生命周期：提交时验证必需章节、快照版本、观点 ID 和成功的分析步骤，合格结果持久化为 `pending_review`；它不会直接替换公共报告。审核命令重新检查数据版本、快照 hash 和门禁后，写入非作者审核记录并将状态推进到 `published`；`/report/full`、报告问答和发布查询只读取最新已批准报告。审核能力不开放为未认证的公网写接口。

分析设计的创新与质量不通过“写得更长”体现，而由有比较基线的发现、按用户群/议题的结构化拆解、指标到原话的证据回溯、替代解释和可继续追问共同体现。MVP 选择有限议题，优先完成分析深度和证据质量，不追求模板自动填满所有方面。

**理由：**团队不需要手写整份离线报告，但仍能审核影响对外结论的分析判断。替代方案包括继续人工写报告、仅将旧稿交给问答模型；二者都无法展示 Agent 从数据生成和检验新发现的能力。无人审核的全自动发布不适用于当前已暴露的质量缺陷。

### 6. API 契约与失败语义

- `GET /api/health`：只检查服务和快照可读性，不调用 LLM；返回服务状态与 `data_version`。
- `POST /api/analyze`：请求 `{question, session_id?, filters?}`；响应 `{answer, stats[], evidence[], applied_filters, data_version, warnings, request_id}`。`stats` 和 `evidence` 由服务端工具结果组装。
- `POST /api/ask`：报告范围问答入口，复用 07 的问答逻辑，并返回已校验锚点与数据版本。
- `GET /api/reports/published/latest`：仅返回当前快照版本下已审核发布的深度报告；待审/驳回报告返回 404。审核与发布由服务端工作区命令完成，不暴露公网写接口。
- 输入无效返回 400；超出请求/上下文限制返回 413；限流返回 429；模型服务失败返回 503；工具或快照错误返回 500 和 `request_id`。错误响应不包含密钥、堆栈或原始数据路径。
- 单会话状态在服务端使用有上限的短期内存缓存；服务重启后会话可重建，历史会话不作为持久业务数据。前端发送会话标识，不发送可执行工具参数。

### 7. 前端采用统一新能源研究工作台品牌系统

建立 AutoInsight「新能源洞察工作台」统一视觉系统：浅色研究画布、深石墨/电网绿为品牌色、能量橙用于重点发现与风险、蓝色用于数据链接，统一工作台与报告内页的色彩、字号、间距和组件。以真实图表、指标口径、筛选维度、证据来源和版本信息表达新能源数据挖掘，不用装饰性霓虹、泛科技背景或割裂的两种材质代替层级。仅展示审核通过的报告内容；报告 iframe 注入同一套品牌令牌。

分析工作台是产品主入口，已发布研究报告是分析成果的阅读入口。报告链接位于分析页标题区，作为次级操作；用户打开报告后，报告在同一主区域展示并提供返回分析。报告页保留章节目录和图表/证据阅读；分析回答渲染为结构化结果卡，分为“统计结果”“支持观点”“分析说明”“适用条件”。卡片顶部显示用户问题和本轮筛选条件，统计区显示指标、口径、样本量和版本，证据区显示可展开原文、观点边界与来源链接。建议问题作为可编辑快捷入口，发送前始终可修改。

桌面端使用内容最大宽度约 1200px 的工作台，分析对话列约 720px，证据和条件可在结果卡内展开；手机端切换单列布局，导航改为可访问的紧凑菜单，不使用固定遮挡输入框或键盘焦点的浮层。图表缩至容器宽度并提供表格/文字摘要。视觉状态除颜色外同时使用标签、图标或文案表达。

**理由：**团队可以围绕三类任务建设统一入口和结果组件，并展示本期审核通过的研究产物，不必复刻临时报告的旧布局。替代方案是将旧报告原样套入一个聊天侧栏；它交付较快，但会把目前已有的内容质量问题带进产品。

### 7.1 内部术语与用户表达使用两套词表

内部 API/工具字段继续使用稳定机器键；新增用户表达目录集中定义指标、维度、证据标识和进度文案。Agent 的系统提示、报告写作技能与前端共同遵循目录：`claims` 显示为“观点条数”，`journey` 显示为“用户所处阶段”，`claim_id` 显示为“证据编号”，比例明确为“负面观点占比（按观点条数）”。任何面向用户的回答、报告或界面状态不得直接透出工具名、技能名、工作流名或内部英文键，除非用户询问技术实现。

### 7.2 默认单焦点内容与报告从属入口

分析是默认主视图，已发布报告作为分析页标题区的次级操作进入同一内容区域。移除顶栏并列报告导航、桌面双栏中的空白报告常驻区和拖动分隔条；报告内容只有在用户明确打开后才占据主区域，且提供返回分析操作。窄屏与桌面采用一致的信息结构。

### 8. 前端交互与无障碍基线

按 WCAG 2.2 AA 作为实现目标：正文对比度至少 4.5:1，支持键盘完成导航、输入、展开证据和复制引用；焦点清晰且不被固定元素遮挡；页面在 320 CSS px 窄视口重排，无需双向滚动读取普通内容。加载时保留用户问题并展示可访问的状态消息；错误说明下一步操作，允许重试；无结果、样本不足和服务不可用都有独立状态。对话输入有明确标签和长度提示；发送后将焦点和屏幕阅读器播报管理在可预测位置。

**理由：**比赛现场可能使用不同尺寸设备、键盘操作和缩放；明确的错误与加载状态也能让智能体行为更可理解。W3C WCAG 2.2 定义了对比度、键盘焦点、重排和目标尺寸标准；GOV.UK Design System 的错误模式强调具体说明问题并保留用户已输入内容。

### 9. 一致性、密钥与日志

发布包中的已批准报告、统计快照、观点索引必须携带同一 `data_version`；启动或健康检查发现版本不一致时服务不得提供分析结果。LLM 密钥仅由部署环境变量注入服务端。公网环境不记录问题全文、模型提示词、引文正文或密钥；可记录请求 ID、耗时、状态码、模型错误类别和工具名称。设置输入长度、单会话轮数和请求速率上限。

公开上线前由 Owner 确认报告、引文、用户标识和原帖链接的展示授权；必要时发布脱敏后的演示数据包。当前仓库是私有数据迁移包，部署不等于数据已获公开授权。

### 10. 深度 Agent 的分析计划与失败语义

深度 Agent 开始执行前必须调用 `submit_analysis_plan`，提交最多六个结构化 workstream。每个工作项绑定白名单 method、可选议题、分析维度及证据要求；服务端校验议题目录与方法参数。方法调用必须与计划中的 method/aspect 完全匹配；报告提交前逐项确认对应方法已通过校验，并确认要求证据的工作项返回了 claim ID。代码解释器只在计划明确 `use_python=true` 时开放；其结果仅在执行成功后进入报告来源记录。

工具错误上限为六次，成功工具调用上限为十八次，Agent 图递归上限为三十二步。超过上限后停止新的分析调用。Agent 未提交通过门禁的报告时，异步任务必须标记失败，不能将没有报告的运行记成成功。确定性报告端点仍可供用户显式选择，深度失败不自动切换链路。

本地 Python 子进程和 AST/I/O 限制只提供演示级隔离，不构成操作系统安全边界。公网部署验收仍需在容器中使用非 root 用户、只读根文件系统、临时可写目录、移除 Linux capabilities、限制 CPU/内存/PID，并进行安全评审；这些部署条件未验证前不得把当前沙箱描述为公网安全。

**验证边界：**计划与完成状态由服务端校验；问题子意图是否被完整拆解仍由模型生成计划并由人工复核，代码无法证明语义覆盖质量。数值/证据可追溯门禁也不等同于结论真实或因果成立。

## Risks / Trade-offs

- **[观点数据字段或来源链接不可用]** → 先用实际数据核对字段、缺失率和链接可展示性；不满足时缩小演示议题或使用经授权的引用，不伪造证据。
- **[LLM 选择错误工具或解释过度]** → 限定工具白名单与参数 schema；结构化统计由后端原样返回；证据不足时拒答。
- **[LLM 生成报告表面完整但洞察浅或错误]** → 每项发现要求比较条件、证据、替代解释和边界；机器门禁只检查可确定部分，至少一名非作者队友审阅再发布。
- **[自动生成文案与数字矛盾]** → 结论关键数字从结构化工具结果渲染，校验指标/版本/证据 ID；人工复核结论排序和解释是否与表格一致。
- **[会话条件漂移]** → 每轮回传并展示生效筛选条件，限制轮数；服务端校验会话上下文中的枚举值。
- **[模型超时/预算消耗]** → 配置超时、速率限制和明确的 503 状态；静态报告独立可用；设比赛演示调用预算。
- **[深度任务并发造成延迟/成本突增]** → 每进程最多两个运行任务；任务达到上限时返回可重试的 429，不启动额外模型调用。
- **[公共链接泄露受限数据]** → 发布前由 Owner 确认授权；默认不暴露原始数据文件和无必要的作者身份信息。
- **[单机内存会话丢失]** → 仅把会话视为短期演示上下文；重启后提示开始新会话，不依赖历史会话完成核心功能。
- **[品牌视觉削弱数据可信感]** → 采用有层级的中性工作画布和有限强调色；设计评审以可读性、来源可见性和窄屏阅读为验收依据。
