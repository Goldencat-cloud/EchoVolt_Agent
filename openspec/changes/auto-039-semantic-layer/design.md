# Design

## Context

动机见 `proposal.md`。这里只记录塑造方案的现状与约束。

### 当前状态

`08_semantic_services` 的数据面由 `db_mirror.py` 生成：读取 `06_reporting/analysis/` 的 4 个冻结文件，写入内部表，再建 5 个 `semantic_*` 视图。业务定义散在六处，彼此不校验：镜像视图 DDL、指标目录字典、分析方法的 SQL 字面量、简报数据字典、中文标签表、工具与技能文档。

下游有三条并行取数路径：镜像视图（分析与沙箱）、直接读冻结文件（`/api/stats`、`/api/claims`）、只读报告文本（报告问答）。第三条不是数据面，本设计不涉及。

### 本轮探索实测（verified）

以下为在固定快照上只读核对的结果，作为方案输入：

| 事实 | 值 |
|---|---|
| 镜像现状 | 议题聚合 16 行 / 精选观点 819 行 / 证据视图 819 行 / 帖子产品范围 15 002 行 |
| 抽取产物 | 9 529 帖、26 936 条观点、18 个议题、5 个情感取值 |
| 身份对齐 | 抽取 `post_id` 与 `posts.source_url` 中的 16 位串完全一致，9 529 / 9 529 命中；URL 中的数字串即采集库 `posts.post_id` |
| 时间可用性 | `posts.published_at` 覆盖 9 994 / 9 994 行，ISO8601 带 `+08:00`，跨 39 个月（2022-10 ~ 2026-10） |

| 口径差异 | 同一议题两级口径差 65%（品牌与口碑 15.5% vs 25.5%） |

### 不可用与未验证（unverified）

- `evidence_ok`（引文回挂校验）只能对 819 条精选观点复现：校验需要原始 block 文本，仓库仅保留 1 288 份冻结输入，且覆盖全部 403 个精选帖。其余 26 000+ 条无法本地重算。
- 生成 `analysis/` 的脚本 `06_reporting/analyze.py` 指向迁移前的路径（`collaboration/...`、`v2/delivery-r3/...`），在当前仓库不可运行；`analysis/` 产物不可重算。这是本次新建构建链路的直接原因。
- 采集库另有 `live_test`（1 帖）与 `backup-20261021` 两套数据，本设计只认 `data/stock`，不做跨库合并。

### 约束

- 8 条在建变更正在修改将要被接线的模块（`analysis_methods.py`、`task_brief.py`、`catalog.py`、`agent_tools.py` 等）；同一文件同一时刻只能有一个写者。
- 业务实现需 Owner 具名与规格评审通过；当前两项均未产生。
- 不新增运行时依赖，沿用标准库与既有依赖。

## Goals / Non-Goals

**Goals:**

1. Agent 可见数据面收敛为 5 个业务数据集，每个数据集的粒度与主键可验证。
2. 语义定义唯一：所有定义只存在于模型工件，代码不内置第二份。
3. 口径成为结构：每一级样本可命名、可查询、可随结果返回，同名不同分母在结构上不可能。
4. 查询只有一个入口，标识符与 SQL 由系统生成，模型输入永不进入 SQL 标识符位置。
5. 构建可重跑、可校验、可拒绝陈旧产物；数值变化由回归用例拦住。
6. 代码分层单向依赖，新增一个指标或维度只改一处。

**Non-Goals:**

1. 不重建上游抽取或归一，不修改 `01`/`04`/`05` 的产物与代码。
2. 不解决"无产品指代观点是否默认归入分析对象"这一业务判断，维持现状并声明为局限。
3. 不对既有 HTTP/MCP 契约做破坏性调整；命名查询保持旧调用可用。
4. 不在本变更内完成接线（改造既有消费方），接线属于后续变更。
5. 不引入外部语义层产品或服务端组件。

## Decisions

### D1. Agent 可见面为 5 个业务数据集，而非现有 5 个镜像视图

**决定**：`claim`（观点）、`post`（发言）、`product`（产品层级）、`mention`（帖子×产品桥接）、`user`（发言者）。

**理由**：这五个是该业务中不可再分的"尺子"——观点衡量态度密度，帖子衡量声量，提及衡量关注与对比，产品衡量对象，用户衡量人群。每删一个都有一类业务问题变成不可答。

**替代方案**：沿用现有镜像视图。否决理由：现有视图是"文件搬运的结果"而非业务实体，其中议题聚合是预聚合，证据视图是事实表的恒等投影，两者都不是业务对象。

### D2. 全量观点落表，分层过滤放在上层

**决定**：26 936 条观点全部进入 `core`，被排除的部分不以"清洗掉"的方式消失。

**理由**：口径阶梯需要每一级的规模可查；一旦底层裁剪，上层无法证明"某一级是什么"。另外口径规则若日后调整，不需要重跑抽取。

**替代方案**：只装 L4 的 3 356 条。否决理由：这就是当前的形态，代价是任何口径问题都无法回答，且换口径必须重建数据。

### D3. 三层数据组织：staging → core → semantic

**决定**：

| 层 | 内容 | 可见性 |
|---|---|---|
| staging | 源产物的直接解析结果，字段原样，不做关联 | 不可见 |
| core | 维度表与事实表，完成身份对齐、时间派生、质量标记 | 不可见 |
| semantic | 由模型生成的视图，携带口径过滤 | **唯一可见** |

**理由**：把"解析"与"业务含义"分开。staging 随上游格式变化而变化，semantic 随业务定义变化而变化，两者变化频率不同，混在一层会让每次上游调整都波及对外契约。

**替代方案**：两层（原始表 + 视图）。否决理由：视图里同时承担解析、连接、口径三种职责，无法单独校验。

### D4. 语义模型是单一声明式工件，不内嵌 SQL

**决定**：模型为单个 YAML 文件，包含 `datasets`、`relationships`、`populations`、`dimensions`、`metrics`、`saved_queries`、`policies`、`snapshot` 八节。代码只解释模型，不重复模型。

**理由**：声明式工件可被非作者评审（Owner 能读懂"这个指标的分母是什么"），可被结构校验，可被多个消费者共享。

**替代方案**：继续用 Python 字典。否决理由：字典可以内嵌任意表达式，评审者必须读代码才能确认口径；且无法阻止"在字典里写死一份 SQL 片段"。

**约束**：模型 MUST NOT 包含任意 SQL 片段。度量表达式限定为列引用、常量、固定聚合函数与白名单布尔条件，由编译器组装。

### D5. 语义视图由模型生成

**决定**：视图 DDL 由 `build/ddl.py` 从模型生成；生成物带"由模型生成"标记；发现同名非生成视图时构建失败。

**理由**：手写视图与模型并存等于第二份定义，正是当前问题的来源。

**替代方案**：只写模型，查询时动态编译，不落视图。否决理由：沙箱需要一个稳定的表名与列集合；且视图能让数据库承担口径过滤，减少应用层重复。

### D6. 口径阶梯作为命名对象，允许 rule 与 frozen 两种来源

**决定**：每级口径有名称、谓词、规模、来源。来源为 `rule` 的由谓词重算，来源为 `frozen` 的由构建期导入确定。当前模型全部为 `rule`，包括 `curated`。

**理由**：`curated` 曾因依赖 `evidence_ok`（需要原始 block 文本）而标为 `frozen`。构建期已在 `core` 层完成引文回挂校验（`evidence_ok` 三态：1 通过 / 0 不通过 / NULL 无法判断），`su7_primary` 只保留 `evidence_ok = 1`，因此 `curated` 由谓词重算不会把"无法判断"当成通过。`curated` 定义为两条分支的并集——拥有者的亲历体验、未拥有者购车前的表达，两支都落在 `su7_primary` 之内；`ownership` 是帖子属性，为让成员判定落在事实行上，构建期在 `fct_claim` 物化一份，切片仍走 `post` 维度。成员关系落到 `claim_population(claim_id, population)`，每级规模可在库内独立计数复核（当前 26 936 → 18 087 → 7 024 → 3 356 → 942 → 819）。

**替代方案**：把 `curated` 标成 `frozen`。否决理由：冻结成员会变成不可复算的清单，模型无法解释"为什么这条在精选里"；`frozen` 保留给确实无法本地重算的情形，当前没有这种口径。

**约束**：口径谓词只能引用事实表已有列；缺失的列必须先物化，不能在查询期假装存在。

### D7. 不向 Agent 暴露预聚合表

**决定**：议题级数字由事实表现算。唯一保留的物化聚合仅用于回归对照，不进入可见面。

**理由**：预聚合把口径决策固化进数据，读者只能接受不能追问。3 356 条量级下实时聚合为毫秒级，没有性能理由预聚合。

**替代方案**：保留聚合并标注口径。否决理由：标注可以改，结构改不了；同一指标两个来源仍可能漂移。

### D8. 查询收敛为单一协议，旧方法降级为命名查询

**决定**：`query(metrics, dimensions, filters, time, order, limit)`。既有 10 个分析组合成为模型中的 `saved_queries`，对外以原名称与参数继续可用。

**理由**：每新增一个问题就要新增一个方法，是当前方法清单膨胀的原因；而 10 个方法中有 8 个本质是一次查询。

**替代方案**：保留方法白名单并扩充。否决理由：校验逻辑会分叉成两套（方法参数校验 + 通用聚合校验），已实际发生。

### D9. 编译器按声明锁定粒度，先聚合后连接

**决定**：执行计划分三步——确定指标所在数据集与粒度 → 在该粒度聚合 → 按声明的关系连接维度。多对多关系一律走"先降粒度再连接"。

**理由**：2.17 倍放大的根因是连接发生在聚合之前。把顺序写进编译器，就不依赖作者记得。

**替代方案**：在 SQL 里用 `COUNT(DISTINCT)` 兜底。否决理由：只能救计数类指标，比率类指标仍会错，且每个查询都要人记得。

### D10. 语义库为独立只读文件

**决定**：构建输出到 `08_semantic_services/data/semantic.db`，以只读方式打开；采集库只作为只读输入。

**理由**：采集库属于 `01` 模块资产，且仓库中存在多套不应混合的数据；语义层不应往上游库加表。物理隔离也比命名约定更可靠。

**替代方案**：在 `ingestion.sqlite3` 内建视图。否决理由：把下游语义绑定到上游库的生命周期，且读写权限无法分离。

### D11. 双键：`post_uid` 作为稳定业务键，`post_id` 作为展示键

**决定**：`post_uid` 为 URL 中的 16 位串，跨数据源对齐用；`post_id` 为论坛数字标识，对外展示与链接用。

**理由**：两套 ID 系统是当前无法从表取数的直接原因；引入稳定业务键可避免同类问题重现。

**替代方案**：只用其一。否决理由：只留数字键会破坏与抽取产物的对齐；只留 hex 键会让外部链接与既有产物失配。

### D12. 结果信封固定包含口径、覆盖、版本、查询标识

**决定**：每个结果返回 `query_id`、`metrics[].population/grain/additive/caliber`、`coverage.thin_buckets`、`model_version`、`snapshot_hash`。

**理由**：报告门禁需要能追溯每个数字；口径文案由字段生成，避免再次出现"文案改了、校验失效"。

**替代方案**：由调用方自行拼接口径说明。否决理由：现有实现就是这样，导致校验退化为中文字符串匹配。

### D13. 代码按职责分包，依赖方向单向

**决定**：

```
08_semantic_services/semantic/
  spec/         领域对象（不可变）：Dataset/Dimension/Metric/Population/Relationship/QuerySpec
  model/        模型加载与校验：loader / schema / validate
  build/        构建链路：staging / core / ddl / lineage
  compile/      查询编译：planner / sqlgen / errors
  execute/      执行与响应信封
  catalog/      目录导出与中文标签
  adapters/     HTTP/MCP/Agent 工具的薄适配（接线阶段填充）
  model.yaml    唯一定义源
```

依赖方向：`spec` ← `model` ← `build`/`compile` ← `execute` ← `catalog` ← `adapters`。上层可依赖下层，下层不得反向引用。

**理由**：当前模块是按"文件平铺 + 同名兼容转发"组织的，`research/` 与根目录同名模块并存，同一函数有两份入口。分层后每个模块只有一种职责。

**替代方案**：继续平铺。否决理由：新增能力时无法判断代码该放哪，重复实现自然出现。

### D14. 编写原则（作为评审检查项）

1. **定义唯一**：指标、维度、口径只出现在 `model.yaml`；代码中不得出现指标名清单。
2. **纯函数优先**：`sqlgen` 不读文件、不连库，输入计划输出 SQL 与绑定参数，可单测。
3. **连接只在一处**：避免多路径各自开库，防止只读约束被绕过。
4. **适配器不含业务**：HTTP/MCP/工具层只做参数编解码与错误码转换，不写口径文案、不写 SQL。
5. **错误码集中**：错误码与可执行提示集中定义，禁止散落字符串。
6. **不可变领域对象**：加载后的模型对象禁止就地修改，避免运行期被悄悄改写。
7. **生成物可识别**：生成的视图与目录文件带版本与来源标记，便于判断是否过期。
8. **单文件不承担两种职责**：一个模块同时做"解析"和"业务判定"即视为待拆分。

### D15. 测试策略分四层

| 层 | 内容 | 作用 |
|---|---|---|
| 模型校验测试 | 引用完整性、基数合法性、口径包含关系、指标维度集合 | 拦截定义错误 |
| 编译契约测试 | 请求 → 计划 → SQL 的确定性；错误码覆盖 | 拦截编译错误 |
| 数值回归 | 固定快照上的基准结果，含各级口径规模 | 拦截口径漂移 |
| 影子比对 | 旧方法与新协议在相同参数下逐行比对；产品分组用例单独标注预期差异 | 证明接线前后等价 |

影子比对中，产品分组用例按 B 项预期**不相等**，该差异需单列并在接线报告中标明，不得混入"通过"。

### D16. 多归属用独立粒度表达，不做隐式改口径

**决定**：一条观点提到 N 个车型时计 N 次，这个口径由独立数据集 `claim_product`（一行 = 观点 × 车型，主键 `(claim_id, product_id)`）承载，并提供 `productClaims` / `productNegative` / `productNegativeShare` / `productPosts` 四个指标。观点级指标（`claims`、`negativeShare` 等）不允许按 `product` 切分。

**理由**：多归属不是连接问题，是归属口径问题。同一次聚合并列不了"观点数"和"观点×车型数"，后者也不可能加回前者。把两种粒度写成两个指标名，读者看名字就知道数字不能相加，这与"口径不同的同一业务概念必须是两个指标"一致。

**实现约束**：`claim_product` 的每行带 `claim_id`，观点口径按主键向下传播即可套用（`carries_scope`），不必复制口径阶梯；车型维度改挂在 `product` 数据集上，经 `claim_product_to_product`（多对一）连接，不再经过 `post→mention`（一对多）。

**替代方案**：在编译期把 `claims` 自动提升到 `claim_product` 粒度。否决理由：同一指标名在不同维度下含义不同，调用方无法察觉，报告数字会静默变化。

### D17. 目录一次导出，大取值空间只给高频值与总数

**决定**：`catalog.describe()` 一次返回数据集、口径（含规模）、维度（含枚举/覆盖）、指标（含口径文案与可切分维度）、命名查询与策略。分类/实体维度的取值按库内频次取；取值数超过 `max_rows` 时不给 `enum`，改给 `top_values` 与 `distinct_values`。

**理由**：目录必须能直接支撑一次合法查询，否则调用方只能靠读代码猜字段。但"把所有取值列出来"在标识类维度上会产出几十万字符的负载（`claim_id` 26 936 个），既无用又拖慢；截断并明确告知总数，比给出一个看起来完整、实则不可信的清单安全。

**约束**：目录不得成为第二份定义——不写指标名清单、不手写口径文案；枚举与覆盖来自库，排除值不出现，空值不进入枚举。`describe.py` 里出现指标名视为回归，有静态用例守住。

## 数据视图与语义模型的映射

### 定义 → 视图

| 模型字段 | 生成的视图成分 |
|---|---|
| `datasets.<id>.relation` | 视图名（对外暴露名） |
| `datasets.<id>.source` | `FROM` 的核心表 |
| `datasets.<id>.primary_key` + 维度列 + 关系端点 + 指标/谓词引用列 | 视图列（显式列表，不用 `SELECT *`） |
| `populations.<id>.filter` | **不进入视图**；构建期求值写入 `claim_population(claim_id, population)` |
| `dimensions.<x>.column` | `GROUP BY` 键与过滤条件（查询期） |
| `dimensions.<x>.excluded` | 查询期排除条件，NULL 安全：空值保留并按 `null_label` 标注 |
| `dimensions.<x>.alias` | 过滤值先归一到规范值，再绑定参数 |
| `metrics.<m>.numerator/denominator` | 聚合表达式（仅在查询期使用，不落视图列） |
| `datasets.<id>.grain` | 生成期校验：视图行的唯一性约束对象 |

口径过滤不写进视图，是因为一个数据集只有一张视图：把某一级口径固化成 `WHERE`，等于让其余各级无法被查询。成员关系改为表，规模可在库内逐级 `GROUP BY` 复核，视图只负责"有哪些列"。

### 视图 → 查询

| 查询成分 | 解析路径 |
|---|---|
| `metrics[]` | 定位数据集 → 按 `claim_population` 过滤口径成员 → 取聚合表达式；比率在同一次聚合内展开分子分母 |
| `dimensions[]` | 校验在该指标的允许集合内 → 取列表达式；沿多对一/一对一方向连接，1:N 一律拒绝（`FANOUT_RISK`） |
| `filters{}` | 逐项校验枚举/实体存在性 → 别名归一 → 生成参数化条件 |
| `time{}` | 定位时间维度 → 校验覆盖区间 → 生成闭区间条件 |
| `order/limit` | 按策略上限裁剪 |

### 交互逻辑（一次查询的生命周期）

```
QuerySpec
  → 校验（指标/维度/口径/枚举/覆盖/上限）        失败即返回错误码，不进入编译
  → 计划（选数据集、定 grain、按基数排序连接）
  → 生成 SQL + 绑定参数                            模型输入不进入标识符位置
  → 执行（只读连接，行数上限）
  → 组装信封（口径字段生成文案、覆盖、薄样本、版本、query_id）
```

## 对下游分析的影响

**更方便**：一次目录描述即可构造合法查询，不需要记忆方法名与参数形态；错误码带可用替代，模型可自我纠正；沙箱与查询协议面对同一套数据集，不必切换心智模型。

**更准确**：粒度由编译器锁定，连接顺序不可绕过；口径随结果返回，报告无法在不标注的情况下混用两级；薄样本被披露而非丢弃；跨口径混用在单次查询层面直接拒绝。

**代价**：目录体积增大（枚举 + 同义词 + 口径阶梯）；首次接入需要改造既有调用点；产品维度相关数字会变化。

## Risks / Trade-offs

| 风险 | 应对 |
|---|---|
| 口径阶梯依赖上游 `status`/`role` 判定语义；上游重跑可能改变各级规模 | 构建期记录源文件哈希与各级规模；回归用例断言规模，变化必须显式更新基线 |
| `evidence_ok` 依赖冻结 block 文本，部分帖子无法判断 | 三态标记；`su7_primary` 只收 `evidence_ok = 1`；无法判断的行不静默进入 `curated` |
| 全量落表使库体积从约 2 MB 增至约 15 MB | 可接受；如后续显著增长，再考虑分区或按需装载 |
| 接线期新旧两条路径并存，可能读错来源 | 生成物带来源标记；影子比对作为接线前置条件；接线前不删除旧路径 |
| 产品维度的数字会变：新口径为"观点×车型"多归属，旧路径走"帖子×提及" | 用独立指标名（`productClaims` 等）表达，不与 `claims` 同名；接线报告中单列受影响报表，由 Owner 确认差异 |
| 与 8 条在建变更的文件冲突 | 本变更以新增文件为主；接线推迟到相关变更合并后，由 Owner 决定顺序 |
| 模型成为单点：模型写错会让所有查询一起错 | 模型校验 + 编译器契约测试 + 数值回归三层拦截；模型变更是代码评审对象 |

## 迁移计划

**Phase 1（本变更范围）**：新增 `semantic/` 包与模型，构建链路只写新库，不改动任何既有模块；产出模型校验、编译契约与数值回归测试。旧路径不受影响。

**Phase 2（影子比对）**：用录制参数对旧方法与新协议逐行比对；除产品分组外的差异必须为零，产品分组差异单独建账。

**Phase 3（接线）**：`research/service.py`、`analysis_methods.py`、`task_brief.py`、`agent_tools.py`、`terminology.py`、`integrations/mcp_server.py` 改为薄壳转调；`verifier.py` 改为读结构化口径字段。接线须在相关在建变更合并后另立变更。

**回滚**：Phase 1 与 Phase 2 不改变生产行为，删除新增文件即可回滚；Phase 3 的每个薄壳保持旧实现可用，可按模块回退。
