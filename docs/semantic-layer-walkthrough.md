# 数据语义层设计讲解（Walkthrough）

> 本文是语义层（`semantic/`）设计的系统性讲解，面向评审者与后续维护者。
> 事实来源：`openspec/changes/auto-039-semantic-layer`、`semantic/model.yaml` 及实测运行结果
>（model_version `2026-11-03.4`，snapshot_hash `74aeb7735973`）。

---

## 0. 一句话定义

> **语义模型是一份声明式工件，它把"业务数字怎么算"——粒度、关系、分母、算法——定义成唯一且可校验的结构；代码只解释它，不重复它。**

它同时扮演三个角色：

| 角色 | 机制 |
|---|---|
| 词典（翻译） | 业务词 → 可执行定义（指标、维度、口径） |
| 守门人（约束） | 非法问法在编译期不可表达，结构化拒绝 |
| 证人（出处） | 每个数字随结果携带口径、版本、快照 |

## 1. 系统架构总览：三横带

```
┌─────────────────────────────────────────────────────────────┐
│  ① 定义层（唯一真源）                                          │
│  ┌──────────────────────────────────────┐                    │
│  │  semantic/model.yaml                 │                    │
│  │  datasets │ relationships │ populations                    │
│  │  dimensions │ metrics │ saved_queries │ policies │ snapshot│
│  └──────────────────────────────────────┘                    │
└───────────────┬─────────────────────────────────────────────┘
                │  生成视图 DDL · 校验每个请求
┌───────────────▼─────────────────────────────────────────────┐
│  ② 数据面（自左向右构建）                                       │
│  [冻结原料] → [解析层] → [台账层] → [语义视图 ×6 + 成员表]       │
│   哈希封存     只翻译不判断   对齐·不删     ★唯一可见★           │
└───────────────┬─────────────────────────────────────────────┘
                │  只读 · 只碰语义关系
┌───────────────▼─────────────────────────────────────────────┐
│  ③ 查询面（自左向右执行）                                       │
│  [Agent] → [校验] → [计划] → [SQL生成] → [只读执行] → [信封]    │
│                              └→ [verifier 复算] → [报告门禁]  │
└─────────────────────────────────────────────────────────────┘
```

两条流：**数据流自上而下**（原料 → 可见面），**请求流自左而右**（提问 → 带出处的数字）。交汇点是语义视图 + 成员表。

三带各交付一样东西：定义层交付**可评审**，数据面交付**可追溯**，查询面交付**可复算**。

## 2. 定义层：`model.yaml` 八节

| # | 节 | 一句话定义 | 回答的问题 |
|---|---|---|---|
| 1 | `datasets` 数据集 | Agent 可见的业务对象，声明粒度（一行代表什么）与主键 | 一行代表什么？ |
| 2 | `relationships` 关系 | 每条连接路径及其基数，据此判定连接是否放大行数 | 连过去会不会翻倍？ |
| 3 | `populations` 口径 | 样本筛选阶梯：名称、谓词、规模、父级 | 这个数字的分母是谁？ |
| 4 | `dimensions` 维度 | 切片轴：类型、取值来源、别名归一、排除值、空值语义 | 能从哪些角度切？ |
| 5 | `metrics` 指标 | 类型 + 口径 + 粒度 + 可加性 + 允许维度白名单 | 怎么算、能不能加？ |
| 6 | `saved_queries` 命名查询 | 查询协议的固定组合（旧方法名兼容入口），不携带计算 | 常用问法存个模板 |
| 7 | `policies` 策略 | 硬上限与禁止面：行数、维度数、薄样本阈值、禁触表 | 最多给多少、不许碰什么 |
| 8 | `snapshot` 快照 | 数据来源路径 + 构建期哈希，防陈旧产物 | 数据是哪一版？ |

关键约束：**模型不含 SQL 片段**——表达式仅限列名、常量与白名单运算。这不是为了优雅，而是为了让不懂代码的评审者也能直接回答"这个指标的分母是什么"。

## 3. 数据面：四阶段

| 阶段 | 原名 | 职责 | 一句话 | 可见性 |
|---|---|---|---|---|
| 冻结原料 | 数据源 | 采集库 + 冻结产物，SHA-256 封存 | 原件在此，谁也不改 | 外部 |
| 解析层 | staging | 格式转表，字段原样 | 只翻译，不判断 | 不可见 |
| 台账层 | core | 身份对齐、维度/事实分表、派生物化、质量记账，**一条不删** | 对齐身份，一条不删 | 不可见 |
| 语义层 | semantic | 6 张模型生成的视图 + 口径成员表 | 货架由模型摆，口径不焊死 | ★唯一可见★ |

真实规模（实测）：`stg_claim` 26 936；`dim_post` 9 994；`fct_claim` 26 936；`fct_claim_product` 27 418；未解析提及 924 条（记账，不静默丢弃）。

### 口径成员表（`claim_population`）

两列表：`(claim_id, population)`，一行 = "某条观点属于某级口径"。

- **构建期**：按模型谓词逐级求值，写入成员名单
- **查询期**：`WHERE claim_id IN (SELECT claim_id FROM semantic_population WHERE population = ?)` —— 口径是参数，不是字面量
- **校验期**：`GROUP BY population` 直接数出各级规模，回归基线断言

> 把"筛选条件"变成"成员名单"：一张视图，六级口径皆可查；分母从措辞变成事实。

### 口径阶梯（五级主线 + 一条支线）

| 级 | 代码名 | 中文名 | 筛选动作 | 规模 |
|---|---|---|---|---|
| L1 | `extracted` | 全量 | 不筛，一条不删 | 26 936 |
| L2 | `su7_linked` | 关联 | 目标产品包含 SU7 | 18 087 |
| L3 | `su7_primary` | 聚焦 | 主对象、无竞品并列、引文回挂通过 | 7 024 |
| L4 | `experience` | **体验 ★主口径** | 体验评价与故障风险 | 3 356 |
| L5 | `firsthand` | 亲历 | 明确亲历 | 942 |
| L6 | `curated` | 精选 | 支线：拥有者亲历 ∪ 未拥有者购车前表达 | 819 |

注意 `curated`（精选）从 L3 分叉，与 L4 是兄弟关系，不是其子集。

## 4. 查询面：五节点流水线

| 节点 | 无上下文定义 |
|---|---|
| **校验** | 计算前对照声明模型检查请求合法性：概念存在性、组合合法性、取值边界、资源上限。非法请求被结构化拒绝（错误码 + 可替代方案），不进入后续阶段 |
| **计划** | 将请求翻译为执行蓝图：定位数据集、锁定粒度、按预声明基数判定连接安全。先聚合后连接，放大路径在此被拒（`FANOUT_RISK`） |
| **SQL 生成** | 以蓝图唯一输入，确定性渲染参数化语句：标识符来自模型、取值走绑定参数、空值与除零显式处理。同蓝图必产出逐字符相同的语句 |
| **执行** | 只读连接运行编译产物，硬性行数上限内返回。唯一接触数据的环节，权限最小：只读、限量、无状态 |
| **信封** | 结果行与解释它的元数据同响应返回：口径文案、单位与分母、薄样本警告、模型版本、快照指纹、查询指纹 |

### 贯穿示例（真实运行）

请求："各议题的负面观点占比，从高到低" →

```json
{"metrics": ["negativeShare", "claims"], "dimensions": ["aspect"],
 "order": [{"field": "negativeShare", "dir": "desc"}], "limit": 5}
```

编译产物（节选）：

```sql
SELECT t0."aspect",
       (1.0 * COUNT(CASE WHEN t0."sentiment"='负面' THEN 1 END)
              / NULLIF(COUNT(*), 0)) AS "negativeShare",
       COUNT(*) AS "claims"
FROM "semantic_claim" AS t0
WHERE t0."claim_id" IN (SELECT claim_id FROM semantic_population
                        WHERE population = ?)
  AND (t0."aspect" IS NULL OR t0."aspect" NOT IN (?, ?))
GROUP BY t0."aspect" ORDER BY "negativeShare" DESC LIMIT ?
```

执行 63 ms，信封返回：

```json
{"rows": [{"aspect": "可靠性与故障", "negativeShare": 0.551, "claims": 98}, ...],
 "caliber": "negative ÷ claims（比率）；口径 experience；不可跨分组相加",
 "population": "experience", "grain": "claim",
 "query_id": "5bb0513a4c984941",
 "model_version": "2026-11-03.4", "snapshot_hash": "74aeb7735973"}
```

报告写法："可靠性与故障的负面观点占比最高，55.1%（54/98）——模型口径 L4 体验类，全量 3 356 条观点。"

### 真实拒绝案例

| 问法 | 结果 |
|---|---|
| 按车型切观点条数 | `DIMENSION_NOT_ALLOWED` + 允许维度清单 |
| 一次查询混用两级口径 | `POPULATION_MISMATCH` + "请改用两个查询" |
| 时间超出覆盖 | `OUT_OF_COVERAGE` + 实际覆盖 2022-10~2026-10 |
| 指标名写错 | `UNKNOWN_METRIC` + 全部可用指标 |

## 6. 设计原则（自检清单）

1. 每个数据集能说出"一行代表什么"；粒度是封闭集合
2. 每条连接路径的基数是声明的；放大由编译器拒绝
3. 每个数字的分母可查；口径是命名对象
4. 同名不同分母在结构上不可能（口径不同即不同指标名）
5. 定义只有一份；代码中出现指标名清单即视为回归
6. 模型里没有 SQL；评审者无需读代码即可确认口径
7. 空值与除零语义显式（`null_label` / `NULLIF`）
8. 结果带出处（模型版本、快照、口径、样本量）
9. 口径文案由字段渲染；手写文案 = 定义与措辞迟早分叉
10. 差异不是一律视为 bug——已知会变的差异单列建账，并标注 verified / unverified
