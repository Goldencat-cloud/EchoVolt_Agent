# 起草分析计划

## 角色与读者

服务对象：处于计划阶段的 Agent。输入：用户研究问题 + 任务简报（覆盖声明 / 数据目录 / 预置基准）。输出标准：一次通过确定性校验的完整草案——覆盖用户问题的全部子问题与比较意图。

## 起草流程（按序执行，完成一步再进入下一步）

1. **读任务简报**：研究请求、覆盖声明、数据目录（枚举清单）、预置基准。议题名、时间范围、品牌口径一律抄自简报，不凭记忆或样例猜测。需要再看数据结构时用 `semantic_overview`；代码分析只属于执行阶段。
2. **探索预览（按需，至多一次）**：拆解前对候选议题调 `semantic_overview(aspects=[...])` 预览数据支撑——样本量 <5 条的议题须在大纲/报告标注"支撑不足"或直接剔除；预览不产生可引用证据，结论只能来自执行阶段的方法与证据工具。
3. **拆解研究问题**：拆成 1-6 个 workstreams——**数量由问题决定，6 是上限不是目标**。
   - 每个工作项必须直接回答用户问题的某个部分；不为"覆盖面"添加与问题无关的议题级深挖。
   - 典型拆法：时间走势类以时间维度工作项为主，议题级取证只在用户点名该议题时加入；对比类围绕对比意图展开；单议题问题就做单议题。
   - 拆解自查：逐项问"删掉这项后，用户问题是否仍完整？"——删掉不影响答案的就是多余工作项。
   - 时间窗口与覆盖区间无交集时：按全区间执行并在报告"限制"说明，不产出无解释的空结果。
4. **映射方法**：所有量化子问题都用语义层聚合（`semantic_aggregate`）表达——占比、计数、时间切片、跨维度交叉只是 metrics/dimensions 的不同组合，没有"方法目录"可选。需要引文佐证的子问题由服务端按计划推导证据需求，执行时再取证。字段契约与合法取值只看工具说明与语义目录，不凭记忆拼字段。
5. **use_python 判断**：默认 false；仅当计划内方法与聚合都确实无法完成必要分析才设 true。设 true 时执行前读 `execute-plan` 技能的写代码参考；use_python 不豁免声明方法——每个工作项的声明方法仍是完成条件，python 仅作交叉/补充。
6. **声明可视化需求**：用户明确要求图表/画图/趋势图时，对应工作项 MUST 在 `visualization` 中声明（占比排序用 bar，时间走势用 line）；只在正文里用文字"画图"不算完成。
7. **提交**：自查覆盖完整、无多余工作项后调用 `submit_analysis_plan`。

## 被拒后

处置契约（一次性修正、重提限制、错误预算）见工具说明，按返回 message 修正后重新提交完整草案。执行中发现计划有误时，如实执行可执行部分，未覆盖部分写进报告"限制"，不擅自改计划。

## 禁止清单（判断类；机制类约束由工具与校验器强制）

- 议题不明：用户问题没有明确支持议题且运行中无澄清通道时，选预置基准中最相关议题执行，并在报告"限制"写明该假设；无法给出任何相关分析时如实报告失败。
- 探索边界：计划阶段只用任务简报与 `semantic_overview` 预览；不据预览内容下结论。
- 能力边界：简报与工具说明未出现的分析能力表示引擎未开放——不在其上起草工作项，用户相关诉求在报告"限制"说明。

## 参考资料

任务简报（开场消息）：覆盖声明、数据目录、预置基准；`submit_analysis_plan` 工具说明：字段契约与参数写法；执行阶段的取证与聚合技巧：`execute-plan` 及其 reference。
