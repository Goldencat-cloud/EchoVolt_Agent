# 实体归一之后：SU7 论坛需求分析路线

日期：2026-10-18。性质：基于当前字段核查和一手资料的分析设计，不是已经跑出的需求结论。当前产品归一结果见 delivery-r3/，原 V2.3 抽取结果保持原样。

## 先做什么

建议下一步交付“可回查原文的 SU7 问题—需求主题库”，首轮优先回答：已购用户在哪些具体使用场景遇到什么问题，想达到什么结果；待购用户有哪些信息缺口、比较条件和购车顾虑。

以单条 Claim 为基本分析材料，连接产品 taxonomy，再建立另一套需求主题层级。产品 taxonomy 解决“说的是谁”，需求主题解决“在什么条件下，什么事情做不好、想改善什么”。两者用映射关联，不把产品配置树当需求分类树。

Voice of the Customer 原始研究把需求识别、需求层级组织与优先级测量分别讨论，也专门研究提及频率是否可以替代重要性。因此，本项目首先输出主题及证据，重要性留给进一步验证，而不是把高频等同于优先开发。[Griffin & Hauser, 1993](https://pubsonline.informs.org/doi/10.1287/mksc.12.1.1)

## 分析视图：直接复用原结果

建议建立独立分析表，不重抽全量帖子。逻辑字段包括：

| 字段 | 来源/含义 |
|---|---|
| claim_key | post_id + claim.id，保留原 Claim |
| product_node_id / role | V2 taxonomy 映射 + 原 target_products.role |
| aspect | 原方面分类，作为初始大类 |
| need_kind | 问题、明确期望、购买顾虑、正向体验、信息转述或其他；新增分析标注，需抽检 |
| attribute_concept | 产品属性名词，例如电耗、后排头部空间、导航播报 |
| observed_problem | 原文支持的具体障碍/不良结果，不把一般负面态度直接当产品问题 |
| desired_outcome | 作者明确希望达到的结果；分析者推导的潜在需求须另标 inferred |
| context | 原 usage_context，或随后经有界复核补标的原文条件 |
| cohort / journey | 帖子时点的作者状态 + 本条旅程；允许未知 |
| evidence / review_state | 原 block、quote、图片说明来源、复核结论 |
| topic_id / topic_version | 需求主题映射及版本，不覆盖原 aspect/content |

新闻、技术机制和泛行业讨论保留在独立背景层。只有对产品使用/选择/期望有具体信息的内容才进入问题—需求候选池。原 Claim 可能包含多项含义，必要时一条 Claim 对应多个分析标签；不要为多标签重复增加独立帖子/作者计数。

## 需求主题如何建立

推荐“已有方面分类 + 人工编码样本 + 语义聚类建议 + 证据复核”的混合方式。

1. 选 100～150 个候选 Claims 作探索样本，覆盖已购/待购/已订/未知、亲历/转述、长短帖、正负评价及不同方面。该样本用于发现标签和边界，不用于宣称全量准确率。
2. 编码属性、问题、期望、场景；建立主题定义、入选与排除例子。比如“续航与能耗 → 实际续航 → 高速长途续航不足”，其下保留冬季/高速/开暖风等条件；不要将车机省电设置和电池故障仅因都含“续航”合成一类。
3. 初版标签覆盖明确主题；在每个 aspect 内对剩余 Claim 的 content + 简短情境生成 embedding，提出相近主题和新主题候选。聚类单位是 Claim，避免整帖把空间、补能和交付混在一起。
4. 核查每个候选主题的代表、边界、反例及离群记录，允许拆分、合并、未归类和多标签。冻结可复核的 topic_version 后才做频次/人群统计。
5. 用独立抽样评估：主题内语义一致性、相邻主题混淆、漏收、误收以及原文支持程度。不要只看 silhouette 或模型生成的主题名称。

作者方法网站将熟悉数据、编码、候选主题、主题检视、命名和写作视为可以反复往返的过程。这支持本项目保留人工主题审查；本路线是工程化内容编码结合主题发现，并不声称等同于完整 reflexive thematic analysis。[Braun & Clarke 方法网站](https://www.thematicanalysis.net/doing-reflexive-ta/)

BERTopic 可提供 embedding 聚类、c-TF-IDF 主题表示、主题合并、按类别和时间观察等组件；官方文档也保留离群点并说明重分配和后续合并的限制。本项目可把它作为候选主题发现工具，不要求每条 Claim 强制归类，也不将 topic probability 当需求真实性概率。[官方 API](https://maartengr.github.io/BERTopic/api/bertopic.html)、[最佳实践](https://maartengr.github.io/BERTopic/getting_started/best_practices/best_practices.html)

## 最先做的五类分析

| 顺序 | 业务问题 | 分析方法 | 交付物 |
|---|---|---|---|
| 1 | 已购用户日常用车的具体问题是什么？ | 当前拥有 × 明确亲历 × 日常使用/售后候选，再逐证据核查 | 场景化问题主题卡与正向/反例 |
| 2 | 同一问题在什么条件下出现？ | 主题 × 使用场景；工况未知单列，缺失较多时只定性描述 | 场景—问题矩阵 |
| 3 | 待购和已订用户分别担心什么？ | 明确未拥有、已订未提、仅试驾分开；比较具体属性及期望结果 | 决策顾虑与信息缺口地图 |
| 4 | 哪些属性是 SU7 相对竞品的争议点？ | 只用原文明确比较；同属性、同场景并保留比较方向 | 属性—车型对比较证据表 |
| 5 | 主题讨论在不同时期怎么变化？ | 每期独立帖数及主题占该期合格语料比例并列，检查抓取覆盖 | 主题趋势及需要进一步核实的变化 |

品牌/价格舆论可另做背景分析；避免最初就让这两类高频内容掩盖具体用车问题。事件前后变化只描述相关性，先检查发帖量、采样区间和新闻转载变化，再考虑是否需要外部资料解释。

## 怎么计数与排序

- 基础单位是独立帖子、独立同平台作者、Claims 三套计数；Claims 表示表达量，不等于人数。每个主题内同帖去重；一个帖子可以进入多个主题，因此主题百分比之和可能超过 100%。
- 主题覆盖率分母必须明确：例如“该期被识别为当前拥有且有合格亲历体验的 SU7 独立帖子数”。分母随人群、时间、证据门变化一起记录。
- 配置未知的内容仍进入车系分析；已知版本作为切片属性；只有精确 specid 才进入具体配置对比。品牌级表达不分摊给 SU7。
- 首轮用可检查的多列比较，不急于合成一个分数：独立帖/作者数、具体场景、亲历依据、原文后果、期望明确性、未解决迹象、相反证据、原始/转载来源。
- 严重度看原文后果，例如安全风险、无法使用、功能受限、不便；sentiment_intensity 只是表达强弱，不能替代严重度。高严重但低频内容可单列调查。
- 浏览、回帖是传播或互动量，不是独立需求人数。主帖语料没有回复正文；不能把回帖数解释成同意该需求的人数。
- 不直接输出市场渗透率、总体满意度、真实故障率、购买转化率或改进 ROI；这些需要额外抽样或业务结果数据。

## 一张主题卡应包含什么

主题定义、对应产品层级、属性、问题/期望、人群、旅程、场景、独立帖/作者/Claim 数及分母；3～5 条可回查引文、至少一个反例或适用边界；明确需求与分析推导分开；最后写待验证问题及建议验证方式。

示例仅用于说明格式，不是本轮发现：“冬季高速长途希望减少补能中断”需要对应真实帖子、低温/高速/里程条件和补能过程证据，才能写为主题卡。不能由负面续航评价自动推导所有车主都需要更大电池。

## 建议的下一项最小交付

先做“SU7 已购用户亲历用车问题与需求地图”：一份分析视图、经复核的初版主题词典、10～20 张有证据的主题卡、一张方面—场景矩阵，以及包含误收/漏收样例的验证记录。

100～150 条是探索编码样本；标签稳定后另留独立评估样本，并对后续高频/高风险主题定向复核。样本数、通过阈值和模型开销是待在下一项分析规格中确定的参数，尚未作为实验授权。本次未训练 BERTopic、未生成 embedding、未让 Qwen 全量重抽、未运行需求聚类。

实现可以继续用 Python + DuckDB/Parquet 保存分析表和可重复 SQL，按需加入 embedding 与聚类。Agent 层再封装“筛选人群、检索主题、聚合计数、取证据、输出主题卡”五种工具。知识图谱可在主题和关系稳定后接入，先把问题、场景和证据结构理顺。
