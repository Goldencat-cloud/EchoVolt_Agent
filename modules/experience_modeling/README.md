# 汽车论坛体验实体 MVP Schema v0.4.0

## 本次更新
- 新增必填字段 `extraction_confidence`，取值范围 0–1，代表模型对结构化抽取正确性的整体把握，不代表体验主张客观为真的概率。未用人工标注校准前，只建议用于排序和抽样复核。
- `evaluation` 保持可选；存在评价时，必须同时输出 `sentiment` 类别与 `sentiment_score` 数值。
- `sentiment` 类别：`positive`、`negative`、`mixed`、`neutral`、`unclear`。没有可识别评价时省略整个 `evaluation`，不把缺失情感标成 `neutral`。
- `sentiment_score` 范围为 -1 至 +1：-1 强烈负面，0 中性或正负总体平衡，+1 强烈正面。它同时反映方向和强度，是模型估计，不是客观产品评分。`unclear` 时必须为 `null`，其他类别必须为数字。

## 必填字段
- `experience_id`：流水线生成的记录 ID。
- `experience_type`：亲历、预期、假设、转述、泛泛观点或不明确。
- `journey_stage`：用户旅程阶段；必须使用预定义枚举。
- `target_attribute`：规范化属性标签 + 原文关键词。
- `description`：中性摘要。
- `evidence`：来源 ID + 原文引句。
- `extraction_confidence`：结构化抽取的整体置信度，范围 0–1。

## 可选字段
- `user_id` / `product_id`：仅引用已存在且能可靠消歧的实体 ID。
- `context.scenario`：具体使用场景，例如“冬季高速”。
- `evaluation`：只在原文表达或明确传达评价时填写，包含 `sentiment`、`sentiment_score`，可选 `text`。
- `event_time`：体验发生时间明确时填写，不能用帖子发布时间代替。

## 情感类别与数值的边界
| 类别 | 含义 | 数值规则 |
|---|---|---|
| `positive` | 正向评价 | -1 至 +1，通常大于 0；按原文估计 |
| `negative` | 负向评价 | -1 至 +1，通常小于 0；按原文估计 |
| `mixed` | 正负评价并存 | -1 至 +1，数值表示净方向；可接近 0 |
| `neutral` | 明确中性表达 | 通常接近 0 |
| `unclear` | 有评价表达，但情感方向难判 | 必须为 `null` |

没有表达评价时不要创建 `evaluation` 对象。因此，“未表达情感”和“中性评价”不同。数值不应假装有过度精确的心理测量意义；初期用于排序、分布和趋势分析时，应保留类别标签作为主要可解释结果。

## 置信度使用边界
`extraction_confidence` 是模型对字段抽取正确性的整体估计，而非“这位用户说的事实为真”的概率。建议先用人工标注数据评估高/中/低置信度样本的实际准确率；完成校准前，只用于优先复核低分样本，不用于直接过滤所有低分记录。

## 用户旅程阶段枚举
| 值 | 含义 | 常见情形 |
|---|---|---|
| `pre_purchase` | 购车前 | 信息搜索、车型比较、购车考虑、试驾 |
| `purchase_delivery` | 购车与交付 | 议价、下单、付款、提车 |
| `ownership_use` | 拥有与日常使用 | 驾驶、续航、充电、停车、车机使用 |
| `maintenance_service` | 维修与售后 | 保养、维修、质保、客服、投诉处理 |
| `resale_repurchase` | 转卖与再次购车 | 卖车、估价、置换、换购 |
| `general_discussion` | 泛化讨论 | 明确为一般性评论，且没有特定旅程阶段 |
| `unknown` | 无法判断 | 原文信息不足 |

## 理论依据与工程化边界
- ISO 9241-210：为用户体验、实际/预期使用及感知和反应提供概念依据。
- ISO 9241-11：为使用情境和任务背景提供概念依据。
- Lemon & Verhoef (2016)：为购前、购买、购后阶段与顾客旅程思路提供参考。
- 七个 `journey_stage` 标签与汽车属性枚举是本项目的工程化分类，不是某一理论原样规定的枚举。
- 情感类别来自常见情感/情绪极性标注实践；数值评分是工程化的连续极性与强度估计，需要用实际语料验证和校准。
- 证据字段用于可追溯性；MVP 不引入复杂溯源结构。

## 抽取规则
1. 同一体验对象的现象和评价合并在一条记录中。
2. 同一帖子存在多个可独立分析的体验属性时拆分多条。
3. 亲历、预期、假设、转述和泛泛观点必须区分。
4. `journey_stage` 每条必填；阶段不明确时用 `unknown`，明确泛化讨论时用 `general_discussion`。
5. 描述中性化，原始关键词和原文证据保留。
6. 不推断未表达的车型版本、使用条件、原因或事件时间。
7. 评价缺失时省略 `evaluation`；有评价时同时输出类别和数值。
8. 每条记录必须输出 `extraction_confidence`，低置信度意味着需要复核，而不是自动判定内容为假。
9. 没有体验时返回空数组；未知的可选字段省略，不用猜测补齐。

## 文件说明
- `experience-record.schema.json`：单条记录 JSON Schema。
- `extraction-output.schema.json`：一条帖子对应 0 至 N 条体验记录的输出 Schema。
- `system-prompt.txt`：抽取提示词。
- `examples.json`：抽取输出示例。
